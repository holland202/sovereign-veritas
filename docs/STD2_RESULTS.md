# STD-2 results: most of OASB does not reach the product you plug in

Registration: [`STD2_PREREG.md`](STD2_PREREG.md), commit `0a273ca`, made before OASB was installed here. Target:
`opena2a-org/oasb` at `fddf2b1` (v0.4.1). Linux x86_64 container, Node v22.22.0, vitest via `npm ci`. Not run on
the S25.

Drafted by Claude (Opus 5.5), which also wrote the adapters and the harness and ran them, at Chad Holland's
direction. Chad has not reviewed it line by line. Nothing has been filed upstream.

## What went wrong, first

- **P1 is REFUTED in this container.** The ARP run gave 243 passed, 1 failed, 1 skipped, not 244 / 0 / 1.
  The failure is `E2E-002 ... should detect a suspicious binary (curl) as a violation`: `Test timed out in
  10000ms`. It failed 3 of 3 reruns. It is an OS-level live-monitoring test, and the registration said E2E
  tests might behave differently in a container. This is probably the environment, but that is not shown.
- **I did not run the registration commit myself.** The commit `0a273ca` carries the exact text I wrote, but
  it was made by something other than my own `git commit`; mine found nothing left to commit. Its timestamp
  (12:51:49) is before OASB was installed, so the order (registered, then run) holds.
- **P5 held, but partly for a reason other than false positives.** Of the 9 baseline tests that fail under
  flag-everything, one is a false-positive check ("should return z-score 0 before baseline is established").
  Most of the rest fail because that adapter keeps no baseline. The real false-positive test, BL-001, is the
  next finding.
- Self-tested: the same author wrote the adapters, the harness and the judgment.

## What it means

- **Only 69 of the 245 tests measure the product you plug in.** The other 153 scenario tests (in 36 files) always
  test ARP, the reference product, whatever `OASB_ADAPTER` names. The 23 scoring-engine tests test the scorer.
  A vendor who runs `OASB_ADAPTER=./my-product.js npm test` gets ARP's results on those 153 and could read them
  as their own.
- **The suite's own "Zero False Positives" test never sees the plugged-in product.** `BL-001: Normal Agent
  Profile - Zero False Positives` constructs ARP directly. Under the flag-everything adapter it passes 3 of 3:

  ```
  silent BL-001 ['passed', 'passed', 'passed']
  flag BL-001 ['passed', 'passed', 'passed']
  ```

- **The 69 that do reach the product work as a benchmark should.** They fail on silence (P3), and they can
  fail on noise (P5).
- `requireCapability()` in `src/harness/capabilities-core.ts` has an empty body (read before registration,
  not run). Gating that relies on it does not skip anything. 5 files use capability gating; whether any of them
  depends on this function was not checked.

Nothing here says ARP is weak, or that any test is wrong about ARP. The finding is about reach: which tests
measure the product plugged into the suite.

A second full run gave identical lines (`results/std2/run_repeat.txt`). A bug in the harness was found and fixed while writing this up: its `--sabotage` pass also overwrote `passing_without_detection.txt` with sabotaged data. The file was regenerated by the second normal run, and the harness now writes nothing under `--sabotage`. Under `--sabotage` the harness refutes P3 and P5 (`results/std2/sabotage.txt`), so it can fail.
