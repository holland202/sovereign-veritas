## 0. What went wrong before this registration (failures lead)

These come from the 2026-10-06 12:20 session. They change how earlier data can be read.

1. **The F16 and COOPMAT2 runs never happened.** llama-cli 0.6.0 stays in an
   interactive chat loop after it answers. The `GGML_VK_DISABLE_MMVQ=1` process was
   still running when the next pasted commands arrived, so the lines meant to start
   the `DISABLE_F16` and `DISABLE_COOPMAT2_DECODE_VECTOR` runs went to the model as chat
   input. Their "outputs" are the MMVQ-flagged process answering pasted shell text.
   The environment variables were never applied. No conclusion may be drawn from them.
2. **No exit code exists for any llama-cli run in that session.** None of them printed
   its `rc=` line. Each process waited at `>` and was ended by hand, which
   probably killed the whole pipeline. The one `rc=0` on screen is the status of a
   comment/echo line, not of llama.cpp.
3. **The garbled ngl-1 outputs are suggestive, not established.** They came from the
   default sampler (temperature > 0, unseeded), with 8 tokens, one sample per
   condition, and no prediction registered. The CPU run under the same sampler was
   coherent. That justifies the hypothesis, not the claim.
4. **Two of my earlier proposals were wrong or unverified.** `GGML_VK_DISABLE_COOPMAT`
   is not in this build (only `..._COOPMAT2_DECODE_VECTOR` is). I also listed Llama 3.2
   3B and sovereign 1.8B as possible quant contrasts. Their headers show both are
   Q4_K_M (`file_type = 15`).
5. **The offload has not been seen in a log.** The 0.6.0 llama-cli prints no
   `offloaded N/M layers` line by default. "ngl 1 ran on the GPU" is inferred
   from the changed output, not observed.

## 2. Question

When llama.cpp 0.6.0 offloads layers to the Adreno 830 through Vulkan, is the output
**numerically correct**? And is the ngl-99 abort deterministic, and where does it start?

Neither is settled by "it ran". The harness can return **CORRECT**. That is the null
result this instrument must be able to produce, and A2b below shows that it can.

## 3. Instruments

Two kernel paths, measured separately because they are different shaders:

- **gen** (single-token decode → *mat-vec* shaders, the family that aborted): greedy
  generation of 32 tokens from a fixed prompt. The tool is chosen once per session
  and recorded: `llama-completion` (with `--temp 0 --seed 1`, `-no-cnv` if offered), else
  `llama-simple` (greedy by construction), else `llama-cli` (with `--temp 0 --seed 1`).
  **stdin is /dev/null** for every process, so the chat loop cannot capture input.
- **ppl** (batched prompt evaluation → *mat-mat* shaders): `llama-perplexity`, 128-token
  context, 4 chunks, over a fixed corpus that the harness writes.

Classification of a GPU cell against the CPU reference cell for the same model and tool:
- **ABORT**: a non-zero or signal exit, or the pipeline-creation error appears in the log.
- **CORRECT (gen)**: the first `min(24, len(ref))` characters of the whitespace-normalized
  greedy output are equal to the CPU reference.
- **CORRECT (ppl)**: `PPL_gpu / PPL_cpu ≤ 1.05`.
- **INCORRECT**: completed, but fails the rule above.
- **UNPARSED / NO_REF / TOOL_MISMATCH / NOT_RUN**: the instrument could not decide. This
  is never counted as either outcome, and a prediction depending on it is INDETERMINATE.
  A cell whose tool is missing is not recorded, and stays NOT_RUN.
- **COMPLETED** (F cells only): did not abort. Correctness is not assessed there.

Constants (frozen): prompt `Explain in one sentence what evidence means.`; N_GEN 32;
match 24 chars; PPL ctx 128, 4 chunks; tolerance 1.05; scramble seed 20261006; scramble
ratio threshold 3.0; timeouts 300 s for gen and 900 s for ppl.

**Tolerance rationale.** Correct GPU backends normally match the CPU perplexity within
about 1%. The garbled samples, if they reflect a real fault, would put the ratio far above 2.
1.05 sits between those two cases, not at the edge of either.

## 6. Predictions (registered before any cell runs)

P4–P7 are **predictions of failure**: they predict that the Vulkan path is wrong.
"n of n held" would therefore not mean anything passed.

| ID | Prediction | Pass criterion | Confidence |
|---|---|---|---|
| P1 | llama.cpp still enumerates the Adreno | preflight `--list-devices` contains `Adreno (TM) 830` | high |
| P2a | **Anti-vacuity, detects wrong:** PPL separates coherent from scrambled text | `PPL(scrambled)/PPL(text) ≥ 3.0` on CPU TinyLlama | high |
| P2b | **Anti-vacuity, returns correct:** the comparator calls a repeat CPU run CORRECT | `gen_cpu_tinyllama_r2` = CORRECT | high |
| P3 | CPU generation works for all three models | rc 0, non-empty text | high |
| P4 | TinyLlama Q4_K_M decode on Vulkan is wrong | `gen_vk1_tinyllama` = INCORRECT | medium |
| P5 | TinyLlama Q4_K_M batched eval on Vulkan is wrong | `ppl_vk1_tinyllama` = INCORRECT | low |
| P6 | Q4_0 decode on Vulkan is also wrong (fault is not Q4_K-specific) | `gen_vk1_q40` = INCORRECT | low |
| P7 | Q4_K_M decode is wrong on a second architecture | `gen_vk1_qwen_q4km` = INCORRECT | medium |
| P8 | The ngl-99 abort is deterministic | all three `cli_vk99_tinyllama_r*` = ABORT with a pipeline name | medium |
| P9 | The abort is monotone in ngl, and ngl 1 does not abort | ABORT set over ngl {1,2,11,21,22,23,99} is upward-closed and excludes 1 | medium |

**Interpretation keys, fixed in advance:**
- P4 held, P5 refuted → the fault is in the mat-vec path only, and batched matmul is fine.
- P4 and P5 both held → the fault is shared (dequant, norm, rope or attention ops), or it is the driver.
- P6 refuted (Q4_0 correct) and P4 held → supports a K-quant-specific kernel fault.
- P6 held → suspicion shifts to llama.cpp 0.6.0 Vulkan × the Adreno driver generally.
- P8 refuted (intermittent) → the abort is not purely a function of the kernel. Check
  MemAvailable per cell, since `ErrorUnknown` from pipeline creation can be resource exhaustion.
- If any G flag turns `gen_vk1_tinyllama` CORRECT, that flag names the faulty path.
  This is a lead to register in VK-2, not a result.

**Labelling rule.** Only a CORRECT GPU cell whose log shows Vulkan in use may be described
as "llama.cpp Vulkan inference on Adreno 830 demonstrated (correct output)". If no
`offloaded N/M layers` line is present, the label must add "offload not evidenced in log".
No speed or energy claim follows from this experiment. Battery current and temperature
are recorded only as a proxy.

## 7. Limits

- Single device, single driver build (`f61dec9117`), package llama.cpp 0.6.0. Not general.
- 24-character greedy agreement can, rarely, fail on a correct backend if fp16 rounding flips
  a near-tie argmax. A PPL cell within tolerance next to an INCORRECT gen cell is the cue to check for that.
- The memory state is not controlled. Swap is about 80% used, and the harness only records it.
- The harness was written by Claude and tested against fake llama binaries in Claude's sandbox.
  That is a self-test only: **NOT VALIDATED on the S25** until this matrix is run there.
